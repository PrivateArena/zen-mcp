# Review: go-mcp Stateless Streamable HTTP Implementation

**Date:** 2026-08-09 · **Reviewer:** Zen (Senior Code Reviewer) + Claude red-team (browser.chat)

## Summary

Reviewed the stateless Streamable HTTP MCP implementation in `internal/server/routes.go` (12 routes, `SetupRoutes`, `postMCP`, `autoDetectWorkspace`, `serverCache`), its supporting server layer (`pool.go`, `patch.go`, `toolslist.go`, `tools.go`, `toolstate.go`), the wiring in `main.go`, and the cross-linking tool `tools/capture.go`. Goal: determine whether the mcp-go `WithStateLess(true)` usage matches the documented pattern for `github.com/mark3labs/mcp-go` v0.48.0 and is correct.

**Blast radius:** `routes.go` is the front door of the entire HTTP surface. Both listeners (filtered MCP :3001, unfiltered CLI :2999) route every MCP interaction — `initialize`, `tools/list`, `tools/call` for all 16 tools, `prompts/list`, resources — through `postMCP` (routes.go:161-190). Downstream: `serverCache` → `newMcpServer` → `RegisterAllTools` → every tool handler. Findings below affect workspace binding of every tool call (F3), memory footprint under multi-workspace load (F2), per-workspace tool enable/disable correctness (F14), collab-capture correctness (F5/F11), and any feature depending on the pool's inflight tracking/reaping — which silently does not run (F1).

**Verified running state:** live `curl -v` against `127.0.0.1:3001` confirms the server is up, `tools/list` returns 200 application/json chunked with no `Content-Length` header; `go test -tags fts5 -race ./internal/server/` passes (8.0s).

## Red-Team Critique (Claude, via browser.chat)

Each point labeled per the reconcile taxonomy:

- **Kept:** F1 dead pool (high confidence), F2 unbounded cache, F4 3x body read, F5 collab map race, F10 transport mislabel. All confirmed with its own reasoning, no material changes.
- **Refined:** F3 (mechanism corrected — autoDetectWorkspace recomputes every call; the actual gap is initialize-only `rootUri`/`workspaceFolders` not read on later calls; confidence raised to ~85%); F6 (functionally safe but non-idiomatic — construct once per cached server); F7 (GET must be 405 per spec and mcp-go's own convention — route into the handler instead of hand-coded 400); F8 (conditional risk; needs live verification — which I closed with `curl -v`: no Content-Length, so risk does not materialize); F9 (elevated to Minor because `net.Listen("tcp", ":port")` binds all interfaces).
- **Added:** F11 double-resolve/stale-closure on the collab race loser path (Major); F12 zen-cap config re-read per capture call (Minor); F13 per-request construction silently discards streamable options (Minor); F14 `ApplyToolStates("", …)` ordering clobbers per-workspace states (Claude: Nit → verified here as Major).
- **Rejected:** F8's Content-Length mismatch — disproven by live test (mcp-go v0.48.0 sends no `Content-Length`, chunked). F7's DELETE=400 was *not* rejected (spec says MAY be 405, so 400 is defensible there; only GET must be 405).

## Open Questions

1. **opencode client request shape (F3 impact):** Does the opencode client send a workspace header/query on *every* request, or only `rootUri` on `initialize`? If the former, F3 is largely theoretical for opencode; if the latter, every tool call after initialize runs against the wrong workspace. Untestable in-session — needs a captured opencode HTTP session.
2. **mcp-go `StatelessSessionIdManager` internals (F6/Q2):** Claude confirmed type existence but not the exact `Generate`/`Validate` bodies. Whether it truly holds no per-connection map affects whether even per-request construction is safe (live behavior suggests yes). Would be closed by reading `server/session_manager.go` — deferred per review constraint (no local library reads).
3. **Per-workspace tool-state intent (F14):** Is per-workspace `.zenmcp/config.json` `enabled_tools` an intended production feature, or legacy? If intended, F14 is a functional bug; if legacy, the redundant `ApplyToolStates("", …)` calls should still be removed. Verify against user expectations.
