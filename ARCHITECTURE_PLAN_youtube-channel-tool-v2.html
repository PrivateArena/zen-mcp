ARCHITECTURE PLAN v2 — tools/youtube.go: a YouTube channel tool driven like a human

Supersedes ARCHITECTURE_PLAN_youtube-channel-tool.md. Same goal (run a real channel end to end), opposite route: every capability is a real page visit through the Firefox bridge. The v1 “call youtubei/v1 in-page” spine is deleted, not adjusted.

Summary

A new MCP tool youtube plus a youtube-automation skill, letting an agent identify the channel, upload a video through YouTube’s own Studio wizard, schedule it, read a watch page’s comments, reply, list the channel’s content, edit metadata and delete — all by navigating to the page, looking at it, finding selectors, clicking and typing, on the user’s authenticated pachoigame container session. No API keys, no OAuth, no cookie export, no yt-dlp, no youtubei/* request, no SAPISIDHASH, no document.cookie auth derivation.

Two rules govern the whole design:

  1. The rule against synthetic traffic. web_eval is permitted only to inspect the DOM (find elements, read visible text, evaluate a wait condition) and to scroll. It is forbidden to fetch/XMLHttpRequest a YouTube or Studio API path. Rationale: a synthetic youtubei POST is indistinguishable from a bot to YouTube’s own risk signals (no BotGuard/poToken, no real pointer/keyboard history), and a false positive costs the channel. The bridge can reproduce a human interaction exactly — DOM-level JS interaction first, trusted_*/native_* only as a human-gated exception (R5) — so there is nothing to gain and a channel to lose.
  2. Probe in the terminal, then freeze into code. No Go page-flow is written before that flow has been executed live, by hand, through zbrowser/zyoutube CLI calls, with each selector copied out of a real probe response. Stages below are ordered so that each one is a complete, shippable capability.

3. The Reconnaissance Protocol (the method every stage uses)

This is the standing procedure for learning any YouTube page and then acting on it. It is the “3 steps” workflow (open → look → interact) formalised with verified commands and the four traps that make naive attempts fail: shadow DOM (E4), the return-first wrapper rule (E10), shell quoting of probe code (E12), and focus-bound actions stealing the OS cursor (R5).

3.1 Steps

R1 — Open the page in the right container and capture provenance.

cat > /tmp/nav.json <<'EOF'
{"action":"navigate","url":"https://www.youtube.com/watch?v=YSNFGgh0aAs&hl=en",
 "container":"pachoigame","new_tab":true}
EOF
zbrowser --json-file /tmp/nav.json | jq -c '{success,id,url,containerId,title,status,error}'
  • Foreground by default (new_tab:true, not back_tab:true) — per the user’s instruction for testing: work in the tab the browser is actually showing. It costs the global bridge turn per call (a foreground new_tab moves the selection ⇒ opensOwnTab is false, internal/bridge/address.go:74-86) and steals focus, which is exactly what we want during a probe: what we see is what the user sees. Why new_tab and not the current tab: container is applied only when a tab is created (action_handlers.mjs:697-722), so navigating an existing tab cannot select pachoigame. Now that index-addressing is proven end to end (E13–E18), this is a preference, not a workaround: background tabs are fully usable for web_eval, read, get_text, screenshot, type and close_tab without touching the user’s selection, which is what upload_status polling and any parallel flow should use. Revisit only if the bridge stops honouring index.
  • Always hl=en — locators are English labels (§Stage 1 “Select files”, “Next”, “Publish”).
  • Record id (t_…) and pass it as index on every later call. index is honoured by web_eval/screenshot/read/get_text/type/close_tab (E13–E18) and it survives other tabs opening/closing; a stale id is a hard tab_not_found, never a silent fallback. Omitting it means “whatever is selected right now”, which a concurrent caller can change.
  • Assert containerId == YoutubeConfig.ContainerId (20) and that url still points at the intended page. A wrong container means the identity is wrong — stop, don’t continue.
  • Probe payloads go through --json-file, never inline --json '…' (E12).

R2 — Settle the page. Prefer element conditions over time:

cat > /tmp/wait.json <<'EOF'
{"action":"wait_for_selector","index":"t_…","byText":"Select files","timeout":20000}
EOF
zbrowser --json-file /tmp/wait.json
cat > /tmp/waitfn.json <<'EOF'
{"action":"wait_for_function","index":"t_…","polling":1000,"timeout":300000,
 "code":"const p = document.querySelector('tp-yt-paper-progress'); return !p || p.getAttribute('aria-valuenow') === '100';"}
EOF
zbrowser --json-file /tmp/waitfn.json

Never wait_for_network_idle on YouTube/Studio. It waits for zero in-flight requests and the Studio SPA keeps beacons rolling, so the call burns its whole timeout and returns a failure — which is why the bridge’s own crawl profile schema settles navigate-mode profiles with wait_ms (resources/skills/firefox-bridge.md). Use wait_for_selector / wait_for_function on the exact text or node you are about to act on, then act. Confirm in Stage 1 and record the outcome. Note: the browser schema has no by_* params (Stage 0.1), so a locator-based wait_for_selector needs --json-file until that is added.

R3 — Look at it. Two channels, used together:

zbrowser --json '{"action":"screenshot","index":"t_…","path":"/tmp/yt_step.png"}'   # then Read /tmp/yt_step.png
zbrowser --json '{"action":"read","index":"t_…"}'                                      # markdown, E3-verified
The screenshot answers “what state is the wizard in / is a dialog blocking / is there an error toast”. The markdown gives quotable text cheaply. read can be 100 KB+ on a watch page — Go code must never pull full-page markdown into a tool reply (1 MiB reply cap, E-table); use get_text with a locator, or a web_eval that returns only the fields it needs.

R4 — Find selectors with a shadow-DOM-aware web_eval probe. The template (verified working against Studio, E4–E6). It walks shadow roots, reports only visible interactive nodes, caps output:

// ARGS-less: paste into {"action":"web_eval","index":"t_…","code":"…"}
const visit = (root, out, depth = 0) => {
  for (const el of root.querySelectorAll("button,a[href],input,textarea,[role],[contenteditable=true],[data-test-id]")) {
    const r = el.getBoundingClientRect();
    if (r.width && r.height) out.push({
      tag: el.tagName.toLowerCase(), role: el.getAttribute("role"),
      label: el.getAttribute("aria-label"), text: (el.innerText || el.value || "").trim().slice(0, 60),
      id: el.id, testId: el.getAttribute("data-test-id"), cls: (el.className || "").toString().slice(0, 60),
      path: cssPath(el),
    });
  }
  if (depth > 12) return out;
  for (const el of root.querySelectorAll("*")) if (el.shadowRoot) visit(el.shadowRoot, out, depth + 1);
  return out;
};
const cssPath = (el) => { const p = []; let n = el; while (n && n.nodeType === 1 && p.length < 8) {
  const host = n.getRootNode().host; const seg = n.tagName.toLowerCase() + (n.id ? "#" + n.id : "");
  p.unshift(seg); n = host || n.parentElement; } return p.join(" > "); };
return visit(document, []).slice(0, 40);

Notes that are load-bearing:

  • The program’s first token must be return, var, let or const. Otherwise frame.js:225-229 wraps it in return (…) and a leading await … / if … dies with SyntaxError (E10). Idiom that always works: const sleep = ms => new Promise(r => setTimeout(r, ms)); await sleep(1500); return ….
  • Use deepQuery(sel, root) (injected, frame.js:224) for single-node lookups — it walks shadow roots; deepQueryAll does not exist in the sandbox (E6), hence the walker in the template.
  • Never return the raw page HTML; the 1 MiB cap turns that into {"raw":…}.
  • Lazy sections (comments, the Studio table) must be scrolled into view first — document.querySelector('#comments').scrollIntoView() then a wait — before any count is trusted (E9/E11: #comments exists with 0 rendered threads until scrolled).

R5 — Act with the most resilient locator, DOM-level first. Selector priority (skill: Selector Priority Guide): byRole+name → byLabel → byText → byName → byAltText → semantic CSS → id → class. Studio ships data-test-id attributes; prefer them over classes when present (record which the page actually has).

zbrowser --json-file /tmp/click.json     # {"action":"click","index":"t_…","byRole":"button","name":"Next"}
DOM-level only, by decision. click, type, select_option, scroll, clear, focus, upload and web_eval are JavaScript-level and tab-queued; trusted_click, trusted_paste, native_*, human_click, key_combo and screenshot are focus-bound — they steal the OS cursor and take the global bridge turn (internal/bridge/address.go:96-124, bridge.go:50-57). Per the user: the non-trusted path is “good enough for interacting, faster and doesn’t steal focus”, so the ladder is one rung deep — click → re-read (R6) → if it did not register, that is a locator_unresolved finding to report (§4.4), not something to escalate past. Focus-bound actions are reachable only when youtube.allowFocusBoundActions is set to true in config.json by a human (default false), and then only as an explicit, one-off, reported step. The single exception worth probing in Stage 2 is the comment composer: it is a contenteditable/paper-textarea surface (E9), and type may not fire the framework’s own input handling — type demonstrably writes .value with focused:false (E16), which Polymer does not always notice. Stage 2’s probe decides between type, a web_eval text assignment + input event, and trusted_paste — and records the choice in the page notes; whatever it settles on is what the code uses, with no runtime escalation. Every typed value is verified by read-back (R6) before the send button is clicked.

R6 — Verify by observation, never by assumption. After any state-changing action, re-run R3 (a targeted get_text/is_visible, or a screenshot when a dialog/animation is involved) and check the thing you expected to change changed. Unverified writes are reported as unverified, never as success.

R7 — Close. close_tab {"index":"t_…"} on a context that survives cancellation (context.WithoutCancel — bridge.go:103-109 already detaches; the Go side must still close on a cancelled request, internal/tools/tabflow.go:83).

3.2 Freezing a probe into code

When a flow has been executed live and every selector came from a real R4 response:

  1. Write the observed page facts into docs/youtube-pages/<page>.md (URL, tab state, selector table with the probe that produced each, the verification text, the failure text).
  2. Implement it once in Go as internal/youtube/pages/<page>.go (a list of typed steps, §4.3).
  3. Wire the action, regenerate wrappers (zexport_cli), and re-run the flow through the tool, not by hand, to prove the code reproduces the probe.

Selectors never observed in a probe are not allowed in code. (v1’s biggest mistake was a SAPISIDHASH formula and endpoint names written from documentation memory; v2’s equivalent rule is “no selector without a probe”.)

Defaults in defaultConfig() (:178), field after Bridge (:125). containerId is data, not a guess: Stage 0 reads it from list_containers and refuses to run if the two disagree.

Read depth (user decision): the default is read everything — maxComments: 0 means “until the thread list stops growing”, simple and predictable on a small channel. MaxScrolls is a runaway guard, not a policy knob: hitting it returns what was read plus truncated:true and the scroll cursor, so the read resumes where it stopped. When the channel grows and a full read gets expensive, MaxComments/MaxScrolls become the tuning point, together with a prioritisation pass (newest / unanswered / top) — explicitly deferred, per the user.

Page.Eval is the single choke point that enforces transport truth, and it is where the “no synthetic request” rule is physically enforced: the embedded programs it may run live in internal/youtube/scripts/*.js, are //go:embed-loaded by name, and are linted in CI for fetch( / XMLHttpRequest / youtubei (test scripts_lint_test.go). Ad-hoc Go-side JS that is not one of those files is not a supported code path.

4.4 internal/youtube/diagnose.go (create) — auto-report, the drift policy

On any locator_unresolved / attach_failed / page_timeout / unverified: capture screenshot + read (truncated to MaxDiagBytes, default 8 KB) + the R4 probe array of the current dialog, persist under <ProjectRoot>/.zenmcp/youtube/diag/<ts>-<action>/, and return WrapErrorWithContext whose message names the locator, lists the closest visible candidates (text/aria-label/data-test-id, ≤ 12 rows) and the file paths. Diagnosis must never spend an upload or mutate the channel. This replaces v1’s schema_drift doctrine: with no fallback route, a loud, self-explaining failure is the only correct behaviour.

7. Key decisions & rejected alternatives

  1. Real browser interaction, one route, zero synthetic requests. Rejected: youtubei/v1 in-page calls (v1’s spine) — token-cheap but indistinguishable from a bot without BotGuard/poToken, and a mis-classification costs the channel; yt-dlp; the bridge request action (default jar + 1 MiB cap); DOM scraping as an API substitute (we scrape to observe our own interaction, which is a different thing).
  2. web_eval is read-only introspection, enforced in-repo. The rule is a lint over embedded scripts (§4.3), not a comment in a doc.
  3. Hybrid shape: skill-first, then freeze. Rejected: (a) skill-only — cadence, journal, provenance assertions and pooled uploads cannot be enforced by prose; (b) a full 13-action Go tool up front — v1’s table was written from an endpoint model that no longer exists, and each page flow must be probed before it can be coded (that is the literal lesson of v1’s row 10).
  4. Stages ordered by capability, not by layer. One page flow per stage, one live consequence per stage, previous stage accepted before the next opens. Rejected: parallel build of journal + wizard + comments + endpoints (v1’s 11-step ladder interleaved transport, endpoints and wizard work).
  5. Probe → notes → code → tool-driven acceptance. A selector never seen in a probe may not enter code; a flow is not done until the tool reproduces what the terminal did.
  6. Auto-report on drift. Rejected: hard-fail without state (unfixable remotely) and a DOM-fallback “second route” (untestable exactly where it would run).
  7. Journal kept, limiter deleted. Cadence/resume protect quota and a long transfer; a “look human” request-spacing limiter exists only to disguise synthetic traffic, which we no longer produce.
  8. No permission flags (confirm, force) — factual guards only (identity assertion, read-back verification, config-file cadence).
